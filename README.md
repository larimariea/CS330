# CS 330 Computational Graphics and Visualization Portfolio Reflection

## How Do I Approach Designing Software?

Working on my CS 330 project changed the way I approach software design because this was one of the first times I had to think about what my code would actually look like visually when it was finished. With a normal program, I usually focus heavily on whether the program works and produces the correct result. With this project, functionality was only one part of it. I also had to think about the placement of objects, their size and proportions, textures, lighting, colors, and how someone would move around and view the scene.

One of the biggest design skills I developed was learning how to take something I could picture in my head and break it down into shapes that could actually be created with code. An object that looks simple in real life can become much more complicated when you have to build it using individual 3D shapes. I had to pay attention to scale, rotation, and position so that the separate pieces looked like they belonged together instead of looking like random shapes placed next to each other.

My design process was very gradual. I did not try to create the entire finished scene at once. I started with the basic objects and shapes and made sure they were positioned correctly. From there, I continued adding more functionality through each milestone. I worked on camera movement, textures, lighting, and the smaller details that made the scene feel more complete. Being able to build the project in stages made a huge difference because I could focus on one problem at a time instead of trying to solve everything at once.

This is something I can carry into future projects. I learned that I do not need to have every detail figured out before I start developing something. It can be much more effective to create a basic version first, test it, and then continue improving it. Breaking a large project into smaller pieces also makes it easier to figure out exactly where something went wrong.

## How Do I Approach Developing Programs?

Developing my 3D scene required a lot more experimentation than I originally expected. One of the biggest development strategies I used was constantly running the program and seeing what my changes actually did. With graphics, code can compile perfectly and still produce something that looks completely wrong. An object could be too large, facing the wrong direction, floating somewhere it was not supposed to be, or partially hidden behind something else. Because of that, testing became something I did throughout the entire development process instead of waiting until the end.

Iteration was a huge part of this project. I would make a change, run the program, look at the result, and then go back into the code to make another adjustment. Sometimes I only needed to change a value slightly before an object looked right. Other times, I realized that the way I originally approached something was not going to work and needed to change it completely.

The milestones made this process easier because each one added another layer to the project. I was not expected to immediately create a completely textured, lit, and interactive 3D environment. I was able to get the basic scene working first and then continue building on it. As I added textures and lighting, I also had to go back and look at things I had already created because the new features sometimes changed how those objects appeared.

My approach to developing code definitely evolved throughout the course. Earlier in the project, I was more likely to change several things when something did not look right and then run the program again. As I became more comfortable with the code, I started making smaller and more intentional changes. I learned to isolate the problem, adjust one thing, and then see exactly what effect that change had.

That made debugging much less confusing. It also helped me understand what my code was actually doing instead of simply trying different values until something worked. By the final project, I felt much more comfortable going back into my code, identifying the section responsible for what I was seeing on the screen, and making adjustments from there.

## How Can Computer Science Help Me in Reaching My Goals?

Computational graphics and visualization gave me experience with an area of computer science that I had not worked with very much before this course. One thing I appreciated about graphics programming was being able to immediately see the relationship between the code I was writing and what appeared on the screen. Changing coordinates, transformations, rotations, lighting, or textures created a visible result.

From an educational perspective, this course helped me understand how concepts that can seem very mathematical or abstract actually have practical uses. Transformations and coordinates are not just numbers in a formula when working with a 3D scene. They determine exactly where an object appears, how large it is, and which direction it faces. Working with these concepts visually made them easier for me to understand because I could actually see what happened when the values changed.

The course also strengthened my problem-solving skills. There were plenty of moments where something did not look the way I expected it to, and there was not always an obvious answer. I had to look at my code, think about what could be causing the problem, test an idea, and keep making adjustments until I found the solution. That type of problem-solving is something I can use throughout the rest of my education, even in courses that have nothing to do with graphics.

Professionally, I may not end up working specifically in computer graphics, but I can still use many of the skills I developed in this course. Learning how to work with unfamiliar code, debug problems, test changes, organize a larger project, and think about the user's experience are all important skills in software development and technology in general.

I also think there is value in simply having experience with different areas of computer science. Before this course, 3D graphics programming was unfamiliar to me. By the end, I had created an interactive 3D scene with objects, textures, lighting, and camera controls. Going from not really knowing how those things worked to having a completed project reminded me that I do not need to already know a technology in order to eventually become comfortable with it.

## Final Reflection

The biggest lesson I am taking away from CS 330 is that software development is not usually a straight path from an idea to a finished program. My project changed constantly while I worked through the milestones. Some things worked much faster than I expected, while other things required a lot of small adjustments before I was happy with them.

I also learned not to see those adjustments as a sign that I had done something wrong. Going back, changing code, testing again, and improving what I already created was simply part of the development process. By the end of the course, I was much more comfortable with that process than I was when I started.

Seeing the final 3D scene was especially rewarding because I knew how many individual pieces had gone into creating it. What appeared as one complete scene on the screen was actually the result of shapes, transformations, textures, lighting, camera movement, user input, and many smaller pieces of code working together.

More than anything, CS 330 helped me become more comfortable with experimenting and figuring things out as I go. I learned how to take something that initially seemed complicated, divide it into smaller problems, and continue working through those problems until I had something complete. That is a skill I know I will continue using throughout the rest of my computer science education and eventually in my professional career.
